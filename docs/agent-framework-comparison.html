TL;DR / 结论先行

没有最好的框架，只有最合适的骨架

把六个项目放在一起看，会发现它们并不是同一类东西：LangChain 是框架，LangGraph 是运行时，Pi 和 Open Harness 是 harness SDK，OpenClaw 和 Hermes 是产品级平台。真正的差异不在“功能多少”，而在四个结构性选择：循环放在哪、状态放在哪、工具怎么注册、UI 怎么隔离。

Scenario A / 固定流程

RAG、客服、文档问答

步骤可预先确定，选 Pipeline / Workflow。LangChain 的链式组合、你自己的 RagPipeline 都够用。

Scenario B / 长任务

需要恢复、审批、分支

选 Graph / Runtime。LangGraph 的 state、checkpoint、interrupt 是这类问题的标准答案。

Scenario C / 产品化

多渠道、插件、定时任务

选 Platform。OpenClaw、Hermes 的 gateway + plugin + profile 结构值得参考，但不适合小服务照搬。

一句话判断

项目一句话定位代码骨架最适合不适合
LangChain从 Chain 走向 Harness 的 Agent 框架Framework + thin harness统一模型/工具接口，快速搭 Agent需要精确控制执行流与状态
LangGraph显式状态图的 Agent 运行时Graph / state machine长任务、可恢复、HITL、分支/循环线性 RAG 流程；会引入不必要的仪式
OpenClaw产品级个人 Agent + 内置 runtime + 插件 SDKPlatform + harness registry多渠道个人助手、插件生态单机小服务；平台复杂度太高
Open Harness同名两派：state-first workflow / code-first SDKWorkflow / Harness用代码组合 Agent、事件回放需要稳定单一 API 的生产项目
Hermes Agent自改进的个人 Agent 产品，单仓库 monolithProduct / platform开箱即用、渠道多、工具多嵌入现有服务；代码面太大
Pi Agent干净的 harness monorepo，runtime/CLI/TUI 分层Harness / runtime编码 Agent、SDK 嵌入、事件流需要内置权限/沙箱；需自己补
方法说明：本文基于公开文档、仓库目录与 API 说明做结构分析，不是性能 benchmark，也不代表项目整体质量排名。版本与目录会变化；结论以“结构原型”为主，而不是某一版实现细节。
框架决定你写代码的姿势，
架构决定你三年后还能不能改得动。 Comparison principle
01
Coordinate system / 坐标系

先分清 Framework、Runtime、Harness、Platform

很多比较是错的，因为把“框架”和“产品”放在同一张表里比。先校准层级：它们解决的问题不同，代码结构自然不同。

层级它拥有什么典型抽象代表不负责
Framework模型/工具/消息的抽象与集成Model、Tool、Message、Middleware、ChainLangChain、CrewAI、OpenAI Agents SDK长期运行、恢复、部署
Runtime执行、状态、恢复、流式、中断Graph、Node、Edge、Checkpoint、InterruptLangGraph、AutoGen Core、Temporal具体工具与业务提示词
Harness模型循环 + 工具 + 会话 + 上下文管理Agent、Session、Tool Registry、Event StreamPi Agent、OpenHarness、Claude Agent SDK、Deep Agents多渠道产品化、组织流程
Platform接入渠道、插件、定时任务、权限、运维Gateway、Adapter、Plugin、Profile、CronOpenClaw、Hermes Agent底层 Agent 算法本身
P
Platform / 产品层渠道 · 插件 · 定时 · 权限 · 运维 —— OpenClaw / Hermes
↓ 产品化能力
H
Harness / 执行外壳循环 · 工具 · 会话 · 上下文 · 事件 —— Pi / OpenHarness / Claude Agent SDK
↓ 长任务与状态
R
Runtime / 运行时状态图 · checkpoint · 中断 · 流式 —— LangGraph / AutoGen Core
↓ 抽象与集成
F
Framework / 框架层模型 · 工具 · 消息 · 中间件 —— LangChain / CrewAI / OpenAI Agents SDK
关键：同一项目可以跨层。LangChain 现在既是 framework，也提供 create_agent 这层 thin harness；OpenClaw 既有 platform，也有内置 runtime；Hermes 既是 product，也自带 harness。分类看它“拥有并维护”什么，而不是它“支持”什么。

先统一几个名称

LangChain / LangGraph

不是 “LongChain / LongGraph”。LangChain 是框架，LangGraph 是它下面的低层运行时；LangChain 1.x 的 agent 构建在 LangGraph 上。

Open Harness 有两个同名项目

本文同时列：Open-Harness/open-harness（Open Scaffold，state-first workflow）与 MaxGfeller/open-harness（OpenHarness，code-first SDK）。两者结构完全不同。

Pi Agent 指 pi.dev 的 harness

GitHub 上有很多 fork 叫 pi-agent；本文以 pi.dev / earendil-works/pi 的 monorepo 为准：ai / agent / coding-agent / tui。

Hermes Agent 指 NousResearch 版本

以 NousResearch/hermes-agent 的 Architecture 文档为准；它是一个完整产品，不是一个轻量库。

02
Samples / 样本速览

六个项目，六种“代码长相”

先不看细节，只抓每个项目的“第一性结构”。这决定了你读它源码时的路径，也决定了你能不能把它嵌进自己的系统。

LangChain

Framework

把模型、工具、消息、中间件标准化；create_agent 是一层可配置的 harness，底层跑在 LangGraph 上。

代码重心 · core / community / partners
循环 · 框架内建 agent loop
扩展 · middleware / integrations

LangGraph

Runtime

把 Agent 工作流建模为共享状态图：state、node、edge、checkpoint、interrupt。控制流显式，可恢复。

代码重心 · graph / pregel / checkpoint
循环 · 图执行 + super-step
扩展 · 自定义 node / subgraph

OpenClaw

Platform

产品级个人 Agent：内置 runtime、harness registry、plugin SDK、会话管理、多渠道接入与工具策略。

代码重心 · src/agents + packages/agent-core
循环 · embedded-agent-runner
扩展 · plugin SDK / harness registry

Open Harness

Workflow / SDK

同名两派：一派是 state-first workflow（events as truth），一派是 code-first agent SDK（Agent / Session / Middleware）。

代码重心 · packages/core + server
循环 · workflow phase 或 agent loop
扩展 · phase / middleware / tools

Hermes Agent

Product

自改进的个人 Agent 产品：单仓库 monolith，AIAgent 门面 + 70+ 工具 + gateway + SQLite/FTS5 + 插件 + cron。

代码重心 · agent / tools / gateway / state
循环 · conversation_loop
扩展 · tool registry / plugins / skills

Pi Agent

Harness

干净的 harness monorepo：AI 接口、Agent 运行时、编码 Agent CLI、TUI 四层分开；事件流与状态管理清晰。

代码重心 · packages/ai · agent · coding-agent
循环 · agentLoop / Agent
扩展 · tools / hooks / steering
读源码的顺序建议：先找“入口与循环”，再找“状态与持久化”，最后找“工具注册与扩展点”。一个 Agent 项目的复杂度，90% 集中在这三处。
03
Dissection / 逐个解剖

代码结构，就是它的世界观

以下目录是按公开文档与 API 归纳的“典型结构”，不是逐文件快照。重点看三件事：循环在哪、状态在哪、扩展点在哪。

LangChain

Framework + thin harness · Python / TS
langchain/ ├── libs/ │ ├── langchain-core/ # Runnable / Message / Tool / Model │ ├── langchain/ # create_agent / middleware / chains │ ├── langchain-community/ # 第三方集成 │ └── partners/ # openai / anthropic / ... ├── docs/ └── tests/
定位
统一模型、工具、消息的抽象层；当前主推 create_agent，把 prompt / tools / middleware 组合成 harness。
循环
Agent loop 由框架内建；复杂控制流下沉到 LangGraph。中间件负责 guardrails、重试、路由、上下文裁剪。
状态
消息状态为主；长期记忆/检查点交给 LangGraph 或外部 store。
扩展
Middleware 是核心扩展点；集成通过 partner packages 接入，避免核心膨胀。
代价
抽象层多、版本演进快；出问题时需要同时理解 LangChain 与 LangGraph 两层。核心逻辑容易“藏在框架里”。
AI-KB借“中间件”治理横切关注点，但不要把主链路建成 LangChain 依赖。

LangGraph

Runtime · Graph / state machine
langgraph/ ├── graph/ # StateGraph / MessagesState / add_messages ├── pregel/ # 执行引擎：super-step / channel / 并行 ├── checkpoint/ # memory / sqlite / postgres checkpointer ├── store/ # 长期记忆 ├── prebuilt/ # ReAct agent / tools ├── types/ # Command / Send / interrupt └── runtime/ # Runtime context / stream
定位
低层编排运行时：把工作流表示为共享状态图，显式控制节点、边、分支、循环与中断。
循环
图执行按 super-step 推进；节点做工作，边决定下一步；Send 做 map-reduce，Command 同时更新状态与路由。
状态
typed state + reducer；checkpointer 在每个 super-step 边界保存，可恢复、可 time travel；interrupt 支持人工审批。
扩展
自定义 node / subgraph / checkpointer；不强制 prompt 或 agent 架构。
代价
线性流程会被 graph 仪式拖重；节点重跑要求幂等；状态 schema 变更需要兼容旧 checkpoint。
AI-KB固定 RAG 不需要 graph；未来 Agent 需要恢复/审批时，再借它的 state + checkpoint + interrupt 思想。

OpenClaw

Platform + built-in runtime · TypeScript
openclaw/ ├── src/agents/ │ ├── embedded-agent-runner/ # 内置 attempt loop / model / compaction │ ├── sessions/ # session manager / resource / tools │ ├── harness/ # registry / selection policy / lifecycle │ ├── agent-hooks/ # compaction safeguard / context pruning │ └── agent-tools*.ts # tool schema / policy / sandbox edits ├── packages/agent-core/ # @openclaw/agent-core：loop / messages / skills ├── src/llm/ # provider registry / streams ├── openclaw/plugin-sdk/ # 插件契约 └── docs/
定位
产品级个人 Agent：内置 runtime 是默认执行器，同时允许插件注册其他 harness（如 codex）。
循环
embedded-agent-runner 负责 attempt loop、模型选择、provider 归一化、compaction、session 接线。
状态
session manager + transcript + resource manifest；模型运行时按 generation 发布，避免半新半旧状态。
扩展
插件只依赖 plugin-sdk/*，不 import src/** 内部；harness registry 按 provider/model 选择 runtime。
代价
平台复杂度高：资源发现、runtime 选择、worker pool、插件生命周期。不适合小服务直接照搬。
AI-KB借“runtime registry + 工具策略 + 插件边界”，不借它的多渠道与插件生态。

Open Harness

同名两派 · Workflow / SDK · TypeScript
Open-Harness/open-harness # Open Scaffold：state-first ├── packages/ │ ├── core/ # agent() / phase() / workflow() / run() │ └── server/ # HTTP / SSE / provider ├── docs/ │ └── concepts.md # events / phases / observers / replay └── examples/ MaxGfeller/open-harness # OpenHarness：code-first SDK ├── packages/ │ ├── core/ # Agent / Session / Conversation / middleware │ ├── provider-chatgpt/ │ ├── provider-vfs/ # 虚拟文件系统 │ ├── react/ │ └── vue/ └── examples/{cli,nextjs-demo,nuxt-demo}
定位
两派都叫 Open Harness，但结构不同：一派把 Agent 当纯函数 + 阶段 + 事件；一派把 Agent 当可组合 SDK + Session + middleware。
循环
Open Scaffold 用 phase 图推进；OpenHarness 用 Agent.run / Session.send，中间件组合 turn tracking / compaction / retry。
状态
Open Scaffold：事件是事实，state 由事件回放派生；OpenHarness：Session 管理上下文窗口、压缩、重试、持久化。
扩展
phase / workflow / observer；或 middleware / tools / subagents / MCP / skills。
代价
命名歧义；两套生态成熟度不同；选型前必须确认你用的是哪一个。
AI-KB借“events as truth + replay/playback”做评测；借 middleware 做横切；但只引入一个明确依赖。

Hermes Agent

Product / monolith · Python
hermes-agent/ ├── run_agent.py # AIAgent 门面 ├── agent/ │ ├── conversation_loop.py # 主循环 │ ├── prompt_builder.py # stable → context → volatile 分层 │ ├── context_compressor.py # 上下文压缩 │ ├── memory_manager.py │ └── trajectory.py # 轨迹导出 ├── tools/ │ ├── registry.py # 自注册工具 │ ├── terminal / file / web / browser / mcp │ └── environments/ # local / docker / ssh / modal / daytona ├── gateway/ # 平台适配 / session / delivery ├── hermes_state*.py # SQLite + FTS5 会话/状态 ├── hermes_cli/ # 命令 / 配置 / auth ├── cron/ · plugins/ · skills/ └── tests/ # 官方文档：~25k tests
定位
开箱即用的个人 Agent 产品：CLI、TUI、gateway、cron、ACP、插件、技能、记忆、轨迹一应俱全。
循环
AIAgent 是同步门面，实际循环在 agent/conversation_loop.py 与 agent/turn_*.py；工具调用后继续 loop。
状态
SQLite + FTS5：会话、消息、lineage、全文检索；prompt 分 stable/context/volatile 三层，配合 Anthropic prompt caching。
扩展
工具在 import 时自注册；toolset 分组；插件可注册 tools / hooks / CLI；memory 与 context engine 是单选的 provider 插件。
代价
单仓库 monolith，状态相关文件极多；产品逻辑（gateway/channels）与 Agent 核心混在一起。嵌入现有服务成本高。
AI-KB借 prompt 分层、上下文压缩、工具注册、SQLite/FTS5；不复制产品级 monolith。

Pi Agent

Harness monorepo · TypeScript
pi-mono/ ├── packages/ │ ├── ai/ # @earendil-works/pi-ai：多 provider LLM API │ ├── agent/ # @earendil-works/pi-agent-core：runtime │ │ ├── agent.ts # Agent：state / events / steering │ │ ├── loop.ts # agentLoop / agentLoopContinue │ │ ├── messages.ts # AgentMessage / convertToLlm │ │ └── tools.ts # AgentTool / parallel / sequential │ ├── coding-agent/ # CLI / 工具 / 会话 / 容器化 │ └── tui/ # @earendil-works/pi-tui └── AGENTS.md / docs/
定位
干净的 harness：AI 层、Agent 层、编码 Agent、TUI 四层分开；可拆开嵌入，也可作为 CLI 使用。
循环
agentLoop 驱动 turn；事件从 agent_start 到 agent_end，工具执行可并行或串行；shouldStopAfterTurn 控制优雅停止。
状态
AgentState：messages / tools / model / thinkingLevel；transformContext 裁剪上下文，convertToLlm 过滤 UI-only 消息。
扩展
AgentTool + beforeToolCall / afterToolCall hooks；steering 与 follow-up 队列支持中途干预。
代价
README 明确：不内置文件/进程/网络权限系统，需要容器或沙箱补边界；偏编码 Agent，不是通用业务 Agent 平台。
AI-KB最接近“干净 harness”的参考：借事件流、convertToLlm、steering；权限必须自己补。

业界常见方案：抽象对比

项目核心抽象代码结构特征一句话评价

04
Archetypes / 五种骨架

归根结底，只有五种代码骨架

项目名会变，抽象会换，但代码的“骨架”只有这五类。识别骨架，比记住 API 更有用。

01

Chain / Pipeline

按固定顺序组合步骤；控制流由代码写死。简单、可预测、易测。

LangChain classic · RAG pipeline
02

Graph / State machine

共享状态 + 节点 + 边；分支、循环、恢复、中断都显式建模。

LangGraph · AutoGen GraphFlow
03

Harness / Runtime loop

模型 + 工具 + 会话的循环；工具 schema、权限、事件流是核心。

Pi · OpenHarness · Claude Agent SDK
04

Platform / Product

网关、渠道、插件、定时、配置、权限；Agent 只是其中一块。

OpenClaw · Hermes Agent
05

Multi-Agent Organization

角色、任务、团队、调度；用组织结构解决复杂任务。

AutoGen · CrewAI
骨架代码长相强项代价什么时候选
Chain / Pipeline线性函数组合；步骤在代码里简单、可测、延迟可控动态分支/恢复难RAG、客服、文档问答
Graph / State machinestate + node + edge + checkpointer显式控制、可恢复、可中断仪式感重、状态 schema 成本长任务、审批、复杂分支
Harness / Runtimeagent loop + tools + events + session工具生态、流式、可嵌入权限/沙箱要自己补编码 Agent、通用工具 Agent
Platform / Productgateway + adapters + plugins + cron产品化完整、渠道多重、耦合、难嵌入个人助手、跨平台产品
Multi-Agentagents + tasks + teams + orchestration角色分工、并行协调成本、调试困难任务天然多角色、可并行

06
Six positions / 六个位置

循环、状态、工具、Prompt、Transport、扩展点

这六个位置决定了一个 Agent 项目是否“好读、好改、好嵌”。下表把六个样本放在同一组坐标里。

项目循环在哪状态在哪工具在哪Prompt 在哪UI / Transport扩展点
LangChain create_agent 内建 loop；复杂流下沉 LangGraph messages；长期记忆/checkpoint 交给 LangGraph/store tools= + MCP；tool schema 自动生成 system_prompt + middleware SDK 调用；无强绑定 UI middleware / integrations
LangGraph 图执行引擎（Pregel / super-step） typed state + reducer + checkpointer node 内的普通函数/工具；不强制 registry 不规定；由 node 自己组装 SDK / Agent Server node / subgraph / checkpointer

最值得学的一点

把“循环”与“业务”分开。Pi 的 agentLoop、LangGraph 的 graph runtime、OpenClaw 的 runner 都不关心你的业务 Prompt；业务通过 tools / nodes / phases 接入。

最常见的错误

把循环写进业务函数、把状态塞进全局变量、把工具注册写成 import 副作用。项目一大，三件事会同时爆炸：不可测、不可恢复、不可扩展。

07
Design choices / 设计抉择

六个抉择，决定你的架构寿命

以下不是“标准答案”，而是从这些项目里提炼出的取舍。每个抉择都给出业界做法与 AI-KB 的建议。

1 · 状态放哪？

业界：LangGraph 用 checkpoint；Hermes 用 SQLite+FTS5；OpenClaw 用 session manager；Pi 用 AgentState；Open Scaffold 用事件回放。

AI-KB：会话/评测继续 SQLite；Agent 状态用可序列化 AgentState + checkpoint，不放进全局变量。

State is a first-class artifact

2 · 循环放哪？

业界：框架/运行时拥有 loop；业务只写 node / tool / phase。Pi 的 agentLoop 是最干净的分离。

AI-KB：RAG 流水线是“无循环 workflow”；未来 Agent 才有 loop。不要为了统一，把 RAG 强行包成 ReAct。

Loop is infrastructure, not business

3 · 工具怎么注册？

业界：LangChain 函数 + schema；Hermes 自注册 registry + toolsets；Pi AgentTool；OpenClaw tool policy + plugin SDK。

AI-KB：用显式 ToolRegistry，每个工具带 schema、权限、超时、幂等标记；拒绝 import 副作用注册。

Typed tools, explicit registry

4 · Prompt 放哪？

业界：Hermes 分 stable/context/volatile 三层；OpenClaw 用模板 + skills；LangChain 用 system prompt + middleware。

AI-KB：Prompt 进 qa/prompts/*.md，带版本、变量、changelog；优化器只能追加受控规则。

Prompts are versioned assets

5 · UI / Transport 怎么隔离？

业界：Pi/OpenHarness 以 SDK 为核心，CLI/React/Vue 只是适配器；Hermes/OpenClaw 有独立 gateway。

AI-KB：FastAPI 路由只做协议转换；页面用模板/静态资源；核心不 import FastAPI。

Transport is an adapter

6 · 扩展点怎么设计？

业界：LangChain middleware；OpenClaw plugin SDK；Hermes plugins/skills；Pi hooks；LangGraph subgraph。

AI-KB：先做 3 个稳定端口（LLM / SearchIndex / Repository），再加 middleware；不要一开始做插件市场。

Ports before plugins

一个最小 Agent loop，应该长什么样

def run(goal: str, ctx: AgentContext) -> AgentResult:
    state = AgentState.new(goal=goal, budget=ctx.budget)
    checkpoint.save(state)

    while state.status not in {"done", "failed", "need_human"}:
        if state.steps >= ctx.max_steps:
            state.fail("max_steps_exceeded")
            break
        if state.budget.exhausted():
            state.fail("budget_exhausted")
            break

        plan = ctx.llm.plan(state)              # 结构化输出
        if plan.kind == "final":
            state.finish(plan.answer)
            break

        tool = ctx.tools.get(plan.tool)          # registry + schema
        ctx.guardrails.check(plan, state)        # 权限 / 参数 / 风险
        result = tool.invoke(plan.args, ctx.tool_ctx)
        state.observe(tool.name, result)
        checkpoint.save(state)

    return state.to_result()

这个 loop 的重点不是代码，而是四个约束：最大步数、预算、工具白名单、可恢复状态。没有这四样，Agent 就是不可运维的循环。

08
Mapping / 对 AI-KB 的启示

Workflow 为体，Harness 为壳，Agent 为翼

AI-KB 当前是一个确定性的多轮 RAG 服务，外加一个受限的优化 Agent。它不需要变成 LangGraph 或 OpenClaw；它需要的是把“未来 Agent 需要的接缝”提前留好。

Now / 现在

确定性 RAG 服务

索引 → 检索 → 融合 → 上下文 → 生成 → 引用校验。步骤固定，可评测、可回滚、低延迟。

Future / 未来

可选的 Agent 外壳

工具注册、状态机、记忆、护栏、轨迹评测。默认关闭，按 profile / 请求灰度。

值得借的六件事

LangGraph · 显式状态

未来 Agent 用 typed state + checkpoint + interrupt；不要用全局变量或裸 dict 保存执行状态。

Borrow the idea, not the dependency

Pi · 事件流

agent_start → turn → tool → agent_end 的事件模型，天然适配流式 UI 与轨迹回放。

Events before callbacks

OpenClaw · 工具策略

工具 schema、权限、before/after hook、runtime registry；把“能做什么”放在代码里，不放在 prompt 里。

Policy at the boundary

Hermes · Prompt 分层

stable / context / volatile 三层，静态部分可缓存；长会话用压缩，而不是无限堆历史。

Context engineering

Open Harness · 事件回放

事件是事实，state 由事件派生；评测可以“录一次、回放多次”，降低 LLM 非确定性带来的测试成本。

Replayable by design

LangChain · 中间件

重试、护栏、路由、上下文裁剪做成 middleware；不要让每个 endpoint 复制样板。

Cross-cutting concerns

不该照搬的六件事

不要为了 Agent 而 Agent

固定 RAG 流程用 workflow 更好；自主循环会增加延迟、成本与不可解释性。

不要复制产品级 gateway

OpenClaw/Hermes 的 25+ 渠道、cron、插件市场，对本地知识库服务是负担。

不要照搬 monorepo 规模

Hermes 的 hermes_state_*.py 与 70+ 工具是产品演化结果，不是起步架构。

不要一开始做多 Agent

多 Agent 的协调、评测、调试成本高；单 Agent + 工具通常足够。

不要暴露裸 shell / 文件工具

Pi 明确不自带权限系统；AI-KB 若加工具，必须白名单、沙箱、人工确认。

不要让核心依赖框架

LangChain/LangGraph 适合做适配层，不适合做领域模型；核心 qa/ 不应 import 它们。

推荐的混合结构

ai-kb-agent/ ├── api/ # FastAPI：协议转换、DTO、页面 ├── qa/ # 确定性 RAG：pipeline / rewrite / context / citation ├── conversations/ # 会话：窗口、摘要、实体槽 ├── analytics/ # 评估、访问、轨迹 ├── retrieval/ # BM25 / 向量 / 融合 / 父子扩展 ├── domain/ # Chunk / Evidence / Answer / Ports ├── infra/ # LLM / Embedding / SQLite / Files ├── agent/ # 未来：默认关闭，按需启用 │ ├── runtime.py # loop + budget + termination │ ├── state.py # AgentState + checkpoint │ ├── tools/registry.py # schema + permissions + timeout │ ├── memory/ # working / episodic / semantic │ └── guardrails/ # input / tool / output / cost └── optimization/ # 现有自优化 Agent，保留为旁路

什么时候从 Workflow 升级到 Agent？

01
任务步骤能否在写代码时确定？
能 → 保持 Workflow；不要引入 Agent loop。
02
是否需要模型自主选择工具/数据源？
否 → RAG/Workflow；是 → 轻量 Harness（单 Agent + 工具）。
03
是否需要跨请求恢复、人工审批、长任务？
是 → 引入 Graph/Runtime 的 checkpoint + interrupt；否则不要。
04
是否有多个天然独立的角色需要并行？
是 → 考虑多 Agent；否 → 单 Agent + 工具优先。
05
是否需要多渠道、插件、定时任务？
是 → 单独做 Platform 层；不要混进 Agent 核心。
结论：AI-KB 的最优结构不是“选一个框架”，而是“保留自己的 workflow 核心 + 借六家的局部思想”。这比直接套 LangGraph 或 OpenClaw 更轻，也比完全自研更稳。

Verdict / 选型结论

按任务形状选，不按热度选

最后给出一张“场景 → 推荐”的表，以及六个样本的一句话判决。用于评审时快速对齐。

你的场景推荐骨架参考项目不要做什么

一句话判决

LangChain

最好的“标准化层”，不是最好的“控制层”。用它的集成与中间件，别把核心逻辑交给它。

LangGraph

长任务 Agent 的标准答案；但固定 RAG 用它，是用起重机搬茶杯。

OpenClaw

产品化最完整的参考；学它的 runtime registry 与插件边界，别学它的体量。

Open Harness

“事件是事实”与“middleware 组合”值得借；先确认你用的是哪一个同名项目。

Hermes Agent

Prompt 分层、上下文压缩、工具注册的活教材；但它是产品，不是库。

Pi Agent

最干净的 harness 结构之一；借事件流与 convertToLlm，权限与沙箱自己补。

不要问“哪个框架最好”，
要问“哪个骨架，最像我的任务”。 Final verdict

B · 术语

术语含义
Agent loop模型调用 → 工具调用 → 观察结果 → 再调用的循环。
Harness围绕模型循环的外壳：工具、会话、上下文、权限、事件、UI 适配。
Runtime负责执行、状态、恢复、流式、中断的底层引擎。
Checkpoint在某个执行边界保存状态，支持恢复、回放、time travel。
HITLHuman-in-the-loop：暂停执行，等待人工审批或修改。
Event sourcing事件是事实，状态由事件回放派生；便于审计、回放、分支。
MCPModel Context Protocol：工具/资源/提示词的标准化接口。
Middleware在 Agent 执行前后插入的横切逻辑：重试、护栏、压缩、追踪。
