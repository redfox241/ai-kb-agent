评测方案
三层体系

本项目是一套本地知识库 RAG 问答服务（Markdown vault → 混合检索 → 多轮问答 → 引用校验）。评测不是附属功能，而是系统的核心回路：线内 LLM 打分落库、离线多轮确定性门禁、Agent 配对 gold-evidence 评测三层并行，并驱动夜间自优化守护与发布门禁。本报告基于 2026-11-19 的代码、设计文档与 27 题实测快照，梳理全貌、核对口径、给出结果。

01

OVERVIEW / 体系全景

三层并行：实时打分、离线门禁、配对实验

评测贯穿"回答 → 打分 → 落库 → 低分入队 → 自优化 → 夜间守护 → 发布门禁"整个闭环。三层各有分工：线内层负责发现坏案例，多轮层负责守住会话体验，Agent 层负责回答"新能力是否真的更好"。

分工 · A
发现问题

线上真实问答的广度覆盖，低分即触发自优化，是"数据飞轮"的入口。

分工 · B
守住底线

发布/合并的确定性门禁，防止 prompt 或检索参数变更造成体验回退。

分工 · C
证明增量

配对实验 + gold 证据召回，回答"Agent 比 RAG 好在哪里"——这是唯一能证明新能力价值的方法。

评测选了"配对 + gold evidence + 多次采样"，明确放弃"只看 LLM 分数"。

03

ONLINE / 线内 LLM 评估

五维加权打分，低分即入队自优化

每次问答完成后异步调用 judge（optimization/utils/scorer.py），严格 JSON 输出，落库 var/db/analytics.db → eval_records。这是唯一在"用户真实流量"上运行的评测层。

落库
eval_records 表

异步评估旁路写入 analytics.db；同步模式供 /ask_eval 与 /eval 页面逐维度展示。

归档
qa_archive

analytics/archive.py 生成 Markdown 归档与 qa_auto_scores.json，与 sqlite 记录互为备份。

联动
低分 → 自优化队列

总分 ≤ 6 自动写入 auto_optimization/logs/ 触发队列；优化器受限 ReAct 只能改白名单参数，且改动必须过夜间 benchmark 守护。

已知风险：judge 单次打分噪声大（同一题实测 10.0 → 8.0 的"假回归"），且无法区分"常识答对"与"知识库答对"。对策已定但尚未实现：3 次采样取中位数、引入 gold evidence 做 grounding（见 §07）。
04

MULTI-TURN / 多轮评测

确定性指标 + 双门禁，参数隔离防串味

多轮链路是"改写 → 检索 → 生成 → 引用 → 会话落库 → 异步摘要"。评测刻意避开 LLM 主观分，用标注字段做确定性判定，任何回归都能定位到具体轮次与具体类别。

指标与目标（设计口径 vs 脚本产出）

指标判定方式设计目标脚本字段现状备注
Rewrite Accuracy改写后 query 包含期望实体且意图正确 / 需改写轮次≥90%rewrite_acc由 Ollama qwen3:4B-Instruct 改写，prompt 资产版本化
Follow-up Recall@5期望文档进入前 5 / 追问轮次≥85%recall5依赖 expect_docs 标注
Citation Precision有效引用 / 总引用≥95%citation_acc复用 qa/citation.py 校验

双门禁与隔离机制

GATE · 合并/上线条件
两个都过才允许合并
  • 多轮核心指标下降 ≤ 5%（--max-drop 5）；
  • 单轮 benchmark 平均分下降 ≤ 2%，且无 tier 掉档；
  • 单轮回归必须与多轮同时跑（benchmark_backfill --check）。
ISOLATION · 与自优化隔离
multiturn.* 命名空间
  • overrides 拆分 params / prompt_rule（单轮）与 multiturn.*；
  • 多轮参数变更必须附带多轮回归，否则禁止提交；
  • 防止优化器"拿多轮换单轮"造成隐性退化。
Judge 改造（设计中）：多轮评测需将上一轮 Q/A 作为上下文传入评分器 score_answer_multi(question, answer, context_turns=None)，prompt 增加"会话上下文"区块——否则"没重复上轮内容"会被误判为不完整。

PAIRED / Agent 配对评测

不只看答案对不对，更要看证据全不全

27 题、6 类、每题带 gold_docs。同一题基线走 /ask_smart、实验组走 /agent/run，逐题配对比较。拒答判定只看结论区，且只对拒答题计分；避免“常识蒙对”和“答案里提了一句未找到”污染指标。

口径修正（2026-11-19）：首轮全量跑出 abstain_acc=0.185，逐条读答案后发现是判定器缺陷：它对全文匹配“未找到”，把大量正确答案误判为拒答，反过来又会把明确拒答的长答案判成未拒答。现已改为只看结论区前 240 字，并且只对拒答题计分；修正后 3/3。旧数字不要与新快照混用。
这张表还读不出的：基线 /ask_smart 不返回 citations 与 usage，所以 citation_rate=1.0 只代表“响应里有来源”，不是引用精度；tokens 与工具步数也无法测。这两项要等 /agent/run 落地后才有意义。
跑评测本身也会写队列：本轮 27 题在 pending_queue.json 留下 5 条低分记录（affected_users=auto_eval）。守护进程当时未运行，已手动清空；若守护在线，这些记录会直接触发自优化。评测入口应增加 no_enqueue 开关，或固定使用独立实例。

06

GATES / 门禁与守护

评测结果必须能拦住坏变更

三层评测通过三道门禁落地为"可执行的否决权"：发布门禁、夜间守护、Agent 上线门禁。分数只是记录，门禁才是评测的意义。

GATE 01
发布门禁 release_gate.sh
  • pytest 全量 + 架构门禁 + 启动健康检查；
  • RUN_BENCHMARK=1 时追加多轮评测对比；
  • 对应 Makefile：make gate。
GATE 02
夜间守护 daily_benchmark_guard
  • 每晚全量 benchmark 对比当日基线；
  • 轻微下降（均分 0.3–1）→ 告警；
  • 明显下降（>1）或单题回退 >3 → 回滚当日 overrides 备份并重启 8000；
  • 平稳 → 刷新基线（"做梦"机制）。
GATE 03
Agent 上线门禁（规划）
  • 多跳组 Evidence Recall ≥ baseline + 0.15；
  • 单跳 10 题不降超 0.3；
  • Abstention ≥ 0.9；
  • make test / arch 全绿；
  • 人工抽检 10 条引用全部可跳原文。

守护决策表

情形判定动作

GAP & ROADMAP / 缺口与路线

尺子校准了一半，P0 之前不写 runtime

方案整体已体系化，但文档明确列出了一批未闭环项。按"会直接污染结论"的优先级排序如下。
